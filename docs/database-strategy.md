# Database Strategy

The Integrity Pro platform uses PostgreSQL for every relational workload. Each
microservice owns its own logical database on a shared server, following the
database-per-service pattern recommended by microservice architectures.

## Database-per-Service

Sixteen services each have a dedicated database (`identity_db`,
`candidate_db`, ... — see `docs/configuration-reference.md`). Rationale:

- **Isolation** — schema changes and failures are contained per service.
- **Ownership** — each service owns its schema; no cross-service joins.
- **Autonomy** — services can be migrated, scaled or rewritten independently.

Sharing a single PostgreSQL instance keeps operational cost low (dev) while the
logical separation preserves the isolation benefits. On production, RDS
PostgreSQL runs multi-AZ with automated backups and PITR.

## Provisioning by Environment

| Runtime | Provisioning | Details |
| --- | --- | --- |
| Local / Docker | `postgres:16` container | `infra/docker/init-databases.sh` creates the 16 databases on first boot |
| Kubernetes dev | StatefulSet (`infra/k8s/postgres.yaml`) | `postgres-init` ConfigMap creates the databases; PVC on `gp3-encrypted` storage class |
| EKS dev/qa/uat/prod | Amazon RDS (`terraform/modules/rds`) | 16 logical databases on one cluster; credentials in Secrets Manager |

## RDS Configuration (qa/uat/prod)

- **PostgreSQL 16.4**, `gp3` storage, provisioned IOPS not required.
- **Multi-AZ** (uat/prod) — synchronous standby for failover.
- **Automated backups** — 14 days (uat) / 30 days (prod) retention, PITR enabled.
- **Deletion protection** enabled (qa/uat/prod) — instance cannot be dropped
  accidentally; requires explicitly disabling the flag first.
- **Encryption** — KMS at rest, TLS in transit (`sslmode=verify-full` with the
  RDS CA certificate in prod).
- **Parameter group** — tuned connection pool limits and `track_activity_query_size`
  for the reactive R2DBC workloads.
- **Enhanced monitoring** (60s interval) and Performance Insights (uat/prod).
- **Rotating master password** — Secrets Manager rotation Lambda (90 days),
  sourced from `terraform/modules/rds/rotate/rotate.py`.

## Connection Handling

Services connect with **R2DBC** (reactive) plus **Flyway** (migrations) using
the JDBC driver. The pool is sized via `DB_POOL_INITIAL_SIZE` /
`DB_POOL_MAX_SIZE` (default 4/16, prod 8/32). Connection strings are built from
environment variables — the exact same jar runs against a local container or
RDS:

```
r2dbc:postgresql://${DB_HOST}:${DB_PORT}/${DB_NAME}?sslmode=verify-full&sslrootcert=/etc/ssl/certs/rds-ca-rsa2048-g1.pem
```

## Migrations

- Flyway migration scripts live in `services/<service>/src/main/resources/db/migration/`.
- Flyway runs at startup, before the reactive pool accepts traffic.
- Naming convention: `V1__init_schema.sql`, `V2__...` (see
  `docs/database/flyway-and-migrations.md`).

## Backup & Restore

| Runtime | Backup | Restore |
| --- | --- | --- |
| Docker | volume snapshot (`docker volume`) | restore snapshot, re-run migrations |
| Kubernetes | `pg_dump` cron or Velero + Restic | `pg_restore` |
| RDS | automated backups + PITR + snapshots | RDS restore → new instance → point DNS |

Full details in `docs/backup-disaster-recovery.md`.

## Access Control

- **Local/Dev** — single `integrity` superuser with a well-known dev password
  (`integrity`), never used outside non-production.
- **EKS managed** — master user (`integrity`) generated by Terraform, stored in
  Secrets Manager, rotated automatically. No IAM database auth in this release
  (would require `rds-iam` auth changes to the JDBC/R2DBC drivers); note it as
  a future enhancement.
- Security groups restrict RDS ingress to the EKS node security group only.

## Future Considerations

- **Vertical sharding** is already in place (database-per-service). Moving any
  service to its own RDS instance is a DNS/config change.
- **Aurora PostgreSQL** is an option for read scaling without application
  changes (compatible protocol).
- **IAM database authentication** would remove password management entirely
  but requires dependency changes in the data layer.
